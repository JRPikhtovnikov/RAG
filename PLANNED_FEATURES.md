# Планируемые улучшения и фичи

Документ содержит roadmap развития RAG-системы.

Статус обновляется вместе с изменениями кода: `[x]` — реализовано, `[ ]` — запланировано.
Разделы без отметки реализации остаются в плане.

Последнее обновление: 21 октября 2026 года.

## Приоритет 0 — безопасность и корректность

### 1. Изоляция документов между пользователями

Сейчас документы и чанки в Elasticsearch не связаны с пользователем, поэтому поиск потенциально работает по общей базе.

План:

- добавить сущность `Document` в PostgreSQL;
- хранить `owner_id`, `document_id` и права доступа;
- фильтровать поиск по пользователю или коллекции;
- добавить роли `owner`, `editor`, `viewer`;
- ограничить просмотр, удаление и переиндексацию документов.

### 2. Полноценное управление документами

Добавить серверное управление жизненным циклом документа:

- `DELETE /documents/{id}`;
- переиндексация;
- повторная обработка;
- отображение ошибки индексации;
- защита от повторной загрузки одного файла;
- сохранение размера, даты загрузки и количества чанков на сервере.

### 3. Миграции базы данных

Перейти от `Base.metadata.create_all()` и ручных `ALTER TABLE` к Alembic.

Это позволит безопасно изменять структуру базы и откатывать миграции.

## Приоритет 1 — качество RAG

### 4. Корректные страницы и ссылки на источники

Сохранять номер страницы при обработке PDF.

План:

- связывать каждый чанк со страницей PDF;
- сохранять координаты найденного фрагмента;
- добавить кнопку «Открыть на странице»;
- подсвечивать найденный текст;
- показывать точные цитаты в ответе.

### 5. Улучшенный гибридный поиск

Текущий поиск использует weighted min-max fusion для dense- и BM25-результатов.

Предлагаемые улучшения:

- Reciprocal Rank Fusion;
- фильтры по документу, главе, типу блока и языку;
- удаление дублирующих и соседних чанков;
- разнообразие источников в финальном top-K;
- отдельная обработка кода, таблиц, определений и обычного текста;
- порог минимальной релевантности.

### 6. Поддержка контекста диалога — базовая версия реализована

Реализовано 21 октября 2026 года:

- [x] Загрузка последних сообщений текущего чата из PostgreSQL с проверкой владельца.
- [x] Передача истории модели с сохранением ролей пользователя и ассистента.
- [x] Переписывание уточняющих вопросов в самостоятельный поисковый запрос с помощью LLM.
- [x] Использование уточнённого запроса для embeddings, BM25/kNN и reranker.
- [x] Поддержка ссылок на предыдущие темы и примеры, например «чем он отличается от Repository?».
- [x] Ограничение памяти: последние 12 сообщений и до 12 000 символов по умолчанию.
- [x] Отсутствие переноса истории между чатами; первый вопрос работает без переписывания.
- [x] Возврат к исходному поисковому запросу при ошибке, таймауте или некорректном результате переписывания.
- [x] Разделение истории диалога и документальных источников в промпте; факты должны подтверждаться текущими фрагментами.
- [x] Автоматические тесты истории, RAG-пайплайна, LLM-сообщений и HTTP-обработчика чата.

Дальнейшее развитие:

- [ ] Автоматическое резюме длинного диалога для сохранения тем за пределами окна последних сообщений.

Настройки: `CHAT_HISTORY_MESSAGES`, `CHAT_HISTORY_MAX_CHARS`, `CHAT_REWRITE_TIMEOUT_SECONDS`.
Значение `CHAT_HISTORY_MESSAGES=0` отключает использование истории.

### 7. Цитирование и оценка уверенности

LLM должен возвращать не только ответ, но и ссылки на использованные источники.

Пример структуры:

```json
{
  "answer": "...",
  "citations": [1, 3],
  "confidence": 0.86
}
```

Это позволит связывать отдельные утверждения ответа с конкретными фрагментами.

## Приоритет 2 — обработка документов

### 8. Фоновая индексация

Перенести конвертацию, чанкинг и генерацию эмбеддингов из HTTP-запроса в фоновые задачи.

Сценарий:

```text
upload → job_id → processing → progress → indexed/failed
```

Нужно добавить:

- идентификатор задачи;
- прогресс обработки;
- повторные попытки;
- отмену задачи;
- уведомление об ошибке.

### 9. Поддержка дополнительных форматов

Backend пока принимает только PDF, хотя frontend предусматривает больше форматов.

Добавить поддержку:

- DOCX;
- TXT и Markdown;
- HTML;
- CSV и XLSX с сохранением структуры таблиц;
- изображений через OCR.

## Приоритет 3 — пользовательские функции

### 10. Коллекции и теги

Позволить группировать документы по темам:

- Python;
- архитектура;
- проектная документация;
- учебные материалы.

Пользователь сможет задавать вопрос по выбранной коллекции.

### 11. Полнотекстовый режим поиска

Добавить отдельную страницу поиска с возможностями:

- просмотр найденных фрагментов;
- подсветка совпадений;
- фильтры;
- сортировка по релевантности и дате;
- переход к странице документа;
- экспорт результатов.

### 12. Обратная связь по ответам

Добавить оценку ответа:

- полезно;
- не полезно;
- неправильный источник;
- ответ не подтверждается документом.

Отзывы можно использовать для анализа качества и формирования evaluation-набора.

### 13. Потоковая генерация ответа

Использовать SSE или WebSocket, чтобы отображать ответ по мере генерации, а не после полного завершения запроса.

Это особенно полезно для длинных ответов и code review.

## Приоритет 4 — code review

Улучшить текущий режим ревью кода:

- подсветка ошибок по строкам;
- группировка замечаний по severity;
- проверка синтаксиса до отправки в LLM;
- сравнение с принципами из загруженных документов;
- сохранение истории ревью;
- экспорт отчёта в Markdown или PDF.

## Приоритет 5 — тестирование и наблюдаемость

### 14. Автоматические тесты

Частично реализовано 21 октября 2026 года:

- [x] 18 тестов контекста диалога: ограничение истории, переписывание запроса, ошибки и таймауты, порядок LLM-сообщений, HTTP-запрос и проверка доступа к чату.

Добавить:

- unit-тесты для chunker’а;
- тесты гибридного поиска;
- тесты авторизации и изоляции пользователей;
- integration-тесты FastAPI;
- frontend smoke-тесты.

### 15. Оценка качества RAG

Создать набор из 30–100 эталонных вопросов и измерять:

- Recall@K;
- MRR/nDCG;
- точность цитирования;
- долю ответов без галлюцинаций;
- latency этапов pipeline;
- стоимость embeddings и LLM-запросов.

### 16. Мониторинг

Добавить:

- `/health` и `/ready` endpoints;
- структурированные JSON-логи;
- метрики времени embeddings, поиска, reranker и LLM;
- tracing запросов;
- счётчики ошибок и неуспешных загрузок;
- мониторинг Elasticsearch и PostgreSQL.

## Приоритет 6 — защита API

- ограничить размер загружаемого файла;
- проверять MIME-тип и содержимое PDF;
- добавить rate limiting для `/query` и `/upload`;
- использовать refresh/revoke-токены;
- хранить JWT в `httpOnly` cookie;
- запретить запуск с дефолтным `JWT_SECRET`;
- добавить защиту от вредоносных и чрезмерно больших PDF.

## Рекомендуемый порядок реализации

1. Изоляция документов по пользователям.
2. Сущность `Document` и настоящий lifecycle загрузки.
3. Удаление и переиндексация документов.
4. Сохранение номеров страниц.
5. Контекст диалога — базовая версия реализована; автоматическое резюме остаётся в плане.
6. RRF, фильтры и дедупликация поиска.
7. Фоновая индексация с прогрессом.
8. Evaluation-тесты и мониторинг.
